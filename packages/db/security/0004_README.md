# Public content and profile privilege release

`0004_public_access_and_profile_columns.sql` is a guarded **operational security plan**, separate from the schema expansion/finalization. It has not been applied to the supplied remote database. Select its release setting only after confirming database/deployment mapping, API role names, current policies/memberships/grants, column projections and rollback/recovery. It requires the inspected Supabase `anon`/`authenticated`, `auth.uid()` and named public/self policies; unexpected targeted policies or reader privileges abort the transaction. The October 3 revision also rejects unexpected policies on `article_tag`, `article_driver`, `article_team` and `article_race`, since an additional permissive policy could bypass their article visibility filter. The dated September 30 fixture hash predates that revision. Current-source application and all four association-policy rejection/rollback cases passed in a separate synthetic PostgreSQL 18.3 WASM fixture; the selected PostgreSQL/Supabase staging release still requires a matching rehearsal.

The release filters public articles to a real publication timestamp at or before now, a cleared/null embargo and `is_premium = false`. Article associations inherit article visibility, including premium-reference exclusion. It removes direct table privileges before granting author **public columns only**, excluding email. `SELECT * FROM author` consequently fails for public roles; consumers must request the safe projection. Authenticated profile access is restricted to one's own row and permitted profile columns. Identity email/provider, subscription expiry, ID updates and deletes are excluded.

`app_user.email` remains required. Restricted browser INSERT therefore cannot create an identity row without trusted server provisioning; this is intentional. Provision the ID/email from the authoritative auth identity server-side, then allow self updates of display name, locale and timezone. Do not weaken the email constraint or grant browser control of identity/entitlement to make a direct upsert succeed. Timestamp/identity/entitlement updates remain server-controlled.

The new `apex_public_reader` is NOLOGIN/NOBYPASSRLS/NOINHERIT and gets an explicit content SELECT allowlist, safe author projection and appropriate RLS policy membership. No private user/prediction/event/ingestion/newsletter ledger access or future-table default grant is supplied. A prior unsafe reader role, inherited public-schema CREATE or object ownership aborts. Audit effective PUBLIC/group/function privileges and creator-role defaults before introducing login credentials through a trusted secret process. This SQL does not create/print a password or change the running credential.

The current owner/BYPASSRLS application connection will continue bypassing these policies. **FORCE RLS cannot constrain BYPASSRLS roles.** Completing protection requires serving public reads through a verified dedicated non-owner credential, while feature writes/ingestion use separately bounded credentials. Check all read queries for explicit author projection before that cutover. Parent database code owns those connection/query changes; this file does not switch them.

Premium rows are excluded for anon, authenticated and the dedicated content reader until a real, separately authorized entitlement reader exists. Ordinary authentication alone grants no premium content access. Any future entitlement reader must verify server-controlled subscription state and use a matched policy/projection before publishing premium access. Article policy changes do not restrict the owner/editorial worker's private draft or premium reads, so public application helpers must also enforce the same filter during the credential cutover.

Before remote rollout, execute the exact SQL in a disposable fixture environment and test publication/future/embargo/draft/premium visibility and associations, author email denial, self-only profile updates, entitlement/identity mutation denial, public-reader denial of private tables and owner bypass. Transaction failure rolls back the release. After commit, reverse only through an explicitly reviewed prior grant/policy matrix; do not restore broad Supabase defaults reflexively.
