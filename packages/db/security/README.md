# Database security source and release boundary

## Release order for a new database (2026-10-26)

| Step | Run as | File | Notes |
|---|---|---|---|
| 0 | private operator | (no file) | Create `apex_owner`, `apex_runtime`, `apex_worker`, `apex_public` with private passwords (attributes in 0005's guard). |
| 1 | `postgres` | [supabase/0000_template_reconcile.sql](supabase/0000_template_reconcile.sql) | **Supabase only.** Replaces the empty template `public` schema (its default ACLs grant every future table to `anon`/`authenticated`/`service_role`, which 0005 rightly refuses, and `postgres` cannot revoke `supabase_admin`'s defaults). Refuses a schema that holds anything. Plain PostgreSQL skips this step. |
| 2 | `apex_owner` | Drizzle journal `../migrations` | `drizzle-kit migrate` or the Drizzle migrator, owner URL on the session pooler (port 5432). |
| 3 | `apex_owner` | [0005_fresh_runtime_roles.sql](0005_fresh_runtime_roles.sql) | Unchanged guarded role release. |
| 4 | `postgres` | [0006_role_session_timeouts.sql](0006_role_session_timeouts.sql) | Role-level `statement_timeout`/`lock_timeout`/`idle_in_transaction_session_timeout`. Supabase's transaction pooler (6543) ignores the client's startup timeouts (measured on apex-staging 2026-10-26: 2 min / none / none, a 16 s sleep completed). Application transactions also set them locally (`src/bounded-transaction.ts`). |

Each step needs its own explicit release setting on the connection. The whole order, every guard, the per-role privilege matrix (allowed and `42501` denied) and the application's SQL paths run in CI against a disposable PostgreSQL 17 over verified TLS: [`../scripts/ci-database-smoke.mts`](../scripts/ci-database-smoke.mts) (job `database` in `.github/workflows/ci.yml`; the script refuses non-loopback hosts). apex-staging was provisioned by hand on 2026-10-25 with the same steps 0-3 (`docs/DATABASE-SETUP.md` in the workspace); a read-only catalog check on 2026-10-26 found no template default ACLs, no browser-role table grants and `public` owned by `apex_owner`. Step 4 has **not** been applied to apex-staging yet (operator decision).

## History

The October 4 empty-install path uses [0005 fresh runtime roles](0005_fresh_runtime_roles.sql) after the four matching Drizzle migrations. A new disposable native PostgreSQL 18.6 instance initialized all 35 tables with RLS and separate non-owner NOINHERIT/NOBYPASSRLS runtime, worker and public roles over verified local TLS. Its fourth migration added only nullable constrained newsletter delivery identity after security installation; no roles or policies were rerun or broadened. This is current fresh-install evidence, separate from the historical supplied database and legacy Supabase policy proposal below. The release refuses preexisting policies, unknown relations/functions, broad managed browser/default ACLs and unsafe role memberships. It grants the sole known event-log sequence only to the worker, omits unavailable videos publicly, restricts web mutation/worker grading columns and exposes only accepted content-hash columns for public score freshness.

Role/password creation is private operator work. `DATABASE_URL` is the web runtime connection; `DATABASE_WORKER_URL` is the separately provisioned job connection and is required in production. No deployment may use migration-owner credentials as either runtime role. Native multi-connection acceptance, managed-host policy integration and backup/restore acceptance are recorded separately rather than inferred from installation.

The supplied database was catalog-inspected read-only in the dated historical audit and must remain unchanged by explicit user instruction. That audit recorded 29 public tables with RLS enabled and a connected table-owning role with BYPASSRLS/CREATEROLE/CREATEDB; this release did not reconnect to refresh that catalog. Neither an application's display filter nor ordinary owner RLS protects against such a credential's privileges. FORCE RLS would not remove BYPASSRLS.

The historical `0001`–`0003` scripts are retained as reviewed source history, **not a current paste-and-run deployment recipe**. In particular, `0002_least_privilege_role.sql` grants broad CRUD/default privileges and permissive policies across public tables; it does not establish separated reader/writer least privilege. Its inline password replacement is not an approved secret-provisioning workflow. Do not execute those scripts on the supplied copy or infer that their presence proves installation.

The legacy guarded proposal is [0004 public/profile access](0004_README.md), separate from [schema upgrade stages](../migrations/README.md). It filters publication/embargo/nonpremium articles and associations, limits author columns, protects app-user identity/provider/entitlement columns and establishes a dedicated reader allowlist. The October 4 guard additionally checks every public relation, sequences, column privileges and RLS-bypassing TRUNCATE/REFERENCES/TRIGGER/MAINTAIN capabilities; owner-executed views outside the allowlist cannot leak private rows. Unexpected effective access fails the whole transaction. It does not change login credentials or the application's running connection, and must not be run on the protected supplied copy.

The September 30 version was tested through real SET ROLE and privilege checks on synthetic fixtures only. The dated fixture artifact records 54 PostgreSQL 16.13 outcomes, SQLSTATE diagnostics and SQL hashes. The October 3 change extends the unexpected-policy preflight to all four article association tables; the older SQL hash does not certify that revision. The October 3 17-case synthetic PostgreSQL 18.3 WASM run tested that dated guarded schema/security revision and actual Drizzle helper SQL, including association-policy rollback and public publication/author-email checks. The October 4 current legacy guard has separate **48-case PostgreSQL 18.3 WASM evidence** in the outer `backend-release-20261004/database/legacy-security-guard-results.json`, with its exact source hash, effective table/column/sequence privileges, owner-view leakage probes and an actual RLS-bypassing TRUNCATE probe. These synthetic legacy checks do not certify the Supabase Data API, deployed credentials, PostgreSQL 17.6 compatibility, network/TLS or production concurrency/load. Rehearse the selected release against a separately authorized matching staging environment. The supplied 17.6 database retained its original roles, grants, rows and schema.

A separately authorized writable staging environment is required for release rehearsal, catalog/column/function/inheritance review, identity provisioning, scoped TLS checks, dedicated reader/writer design and matched application cutover. The new browser profile grants intentionally cannot provision the NOT NULL email field; identity creation remains a trusted server task. Premium content remains hidden publicly until a real entitlement reader exists. Confirm effective column privileges as well as table ACLs, because revoking table-level privileges alone does not erase older column grants.

The local archive restored successfully into the isolated container with ownership/ACL replay disabled, but its restored public schema had zero RLS-enabled tables and zero policies. Backup recovery must therefore restore and validate reviewed security state separately; successful row/schema restoration is not a security recovery guarantee.
